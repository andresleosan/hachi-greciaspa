# Firestore Schema

Documento de referencia de las colecciones de Firestore del proyecto `hachi-greciaspa`. Mantenido en sincronía con el código; cualquier cambio de schema debe reflejarse acá y en `firestore.rules`.

Última actualización: 2026-08-05 (Fase 3, mascotas y modelo de recordatorios).

## Convenciones

- Todos los timestamps usan `serverTimestamp()` desde el SDK cliente.
- Los "snapshots" (`serviceName`, `userName`, `price` en `reservas`) se guardan por inmutabilidad histórica: si el servicio cambia de nombre o precio después de creada la reserva, la reserva conserva los valores del momento de creación.

## Colecciones

|---|---|---|---|

**Custom claims (Auth):** opcional `admin: true` en el token, complementario al role en Firestore. `set-admin.js` lo setea. Las rules de `isAdmin()` loen ambos.

### `reservas/{resId}`

Citas reservadas. Es la colección central de Fase 2.

| Campo | Tipo | Generated by | Notas |
|---|---|---|---|
| `userId` | string | client (auth.uid) | dueño de la reserva |
| `userName` | string \| null | client | snapshot del displayName |
| `userEmail` | string \| null | client | snapshot del email |
| `serviceId` | string | client | FK a `servicios/{docId}` |
| `mascotaId` | string \| null | client | FK opcional a `mascotas/{mascotaId}`; debe pertenecer al mismo usuario |
| `serviceName` | string | client | snapshot del nombre |
| `price` | number \| null | client | snapshot del precio |
| `date` | string | client | ISO "YYYY-MM-DD" |
| `timeSlot` | string | client | "HH:mm" 24h |
| `durationMin` | number | client | |
| `notes` | string \| null | client | comentarios del cliente |
| `empleadoId` | string \| null | Functions/Admin SDK | empleado asignado; los documentos legacy pueden omitirlo |
| `status` | 'pending' \| 'confirmed' \| 'cancelled' \| 'completed' | client/admin | default 'pending' |
| `createdAt` | Timestamp | client | `serverTimestamp()` |
| `createdBy` | 'client' \| 'admin' | client | qué flujo originó la reserva |

**Índices:** compuestos `userId ASC + createdAt DESC` ("mis reservas"), `userId ASC + mascotaId ASC` (historial por mascota) y `serviceId ASC + date ASC + timeSlot ASC` (detección de doble-booking) están en `firestore.indexes.json`.

**Reglas:** ver `firestore.rules:37-62` y ADR-002. El cliente solo puede crear una reserva propia con `empleadoId` ausente o `null`; no puede agregar, cambiar ni quitar ese campo después. El propietario solo puede cancelar con el cambio exacto `status -> 'cancelled'` cuando la reserva está `pending` o `confirmed`; las escrituras directas del cliente sobre `date`/`timeSlot` son denegadas y no puede cambiar campos adicionales. `rescheduleMyReserva` llama exclusivamente a la callable `rescheduleReserva`, que usa Admin SDK y es la autoridad para validar fecha/hora futura y disponibilidad del slot en una transacción server-side. Admin conserva la edición completa y la asignación automática también usa Admin SDK.

Los documentos existentes sin `empleadoId` son compatibles y se interpretan como `null`. El backfill opcional de abajo solo normaliza esa ausencia; nunca elige ni asigna un empleado.

### `recordatorios/{id}`

Registro de control de recordatorios de cita. El ID es determinístico, con el formato `reminder-${encodeURIComponent(reservaId)}`, para que las ejecuciones horarias reutilicen el mismo documento y no envíen recordatorios duplicados.

| Campo | Tipo | Generated by | Notas |
|---|---|---|---|
| `reservaId` | string | Functions | FK a `reservas/{resId}` |
| `status` | 'pending' \| 'sent' \| 'failed' | Functions | estado del envío |
| `attempts` | number | Functions | intentos acumulados; máximo operativo de tres |
| `scheduledFor` | Timestamp | Functions | fecha y hora objetivo del recordatorio |
| `sentAt` | Timestamp \| null | Functions | instante de envío exitoso |
| `lastAttemptAt` | Timestamp \| null | Functions | último intento de envío |
| `lastError` | string \| null | Functions | categoría de error sanitizada |
| `processingLockUntil` | Timestamp \| null | Functions | vencimiento del lock transaccional temporal |
| `processingToken` | string \| null | Functions | token único que permite aplicar solo la transición del worker dueño del lock |
| `nextAttemptAt` | Timestamp \| null | Functions | no se intenta antes de este instante tras una falla retryable |
| `providerMessageId` | string \| null | Functions | ID devuelto por Resend en el envío exitoso |
| `createdAt` | Timestamp | Functions | creación del registro |
| `updatedAt` | Timestamp | Functions | última transición del registro |

**Lifecycle:** Functions crea el documento en `pending` con `attempts: 0`, `processingToken: null`, `nextAttemptAt: null` y `providerMessageId: null`, adquiere un lock temporal antes de cada envío y aumenta `attempts`. Cada adquisición asigna un token único; las transiciones finales solo se aplican si conservan ese token. El ID determinístico `reminder-${encodeURIComponent(reservaId)}` también se envía como la clave externa de idempotencia del proveedor. En éxito cambia a `sent`, establece `sentAt` y conserva el `providerMessageId`; en una falla retryable cambia a `failed`, conserva una categoría sanitizada en `lastError`, establece `nextAttemptAt` con backoff acotado y libera el lock. En una falla permanente o éxito se limpia `nextAttemptAt`. Las reservas no se modifican por un fallo de email. Los reintentos posteriores solo proceden mientras `attempts < 3` y después de `nextAttemptAt`.

**Ownership and visibility:** solo Firebase Functions mediante Admin SDK crea o actualiza estos documentos; el Admin SDK no depende de los permisos de cliente. Un administrador puede leerlos para operación y debugging. Guest y client no tienen lectura ni escritura; las reglas mantienen `allow write: if false` porque las escrituras de Functions bypassan las reglas de cliente.

**Rollback:** el cambio es aditivo. Para revertirlo, deshabilitar y retirar el scheduled function, conservar `recordatorios` para auditoría y, si corresponde, retirar por separado el índice agregado. No borrar documentos ni ejecutar una migración destructiva.

### `confirmaciones/{id}`

Registro de control del email inmediato de confirmación. El ID es determinístico, con el formato `confirmation-${encodeURIComponent(reservaId)}`, para que los reintentos del trigger reutilicen el mismo documento y no reenvíen una confirmación ya entregada.

| Campo | Tipo | Generated by | Notas |
|---|---|---|---|
| `reservaId` | string | Functions | FK a `reservas/{resId}` |
| `status` | 'pending' \| 'sent' \| 'failed' | Functions | estado del envío |
| `attempts` | number | Functions | intentos acumulados; máximo operativo de tres |
| `sentAt` | Timestamp \| null | Functions | instante de envío exitoso |
| `lastAttemptAt` | Timestamp \| null | Functions | último intento de envío |
| `lastError` | string \| null | Functions | categoría de error sanitizada |
| `processingLockUntil` | Timestamp \| null | Functions | vencimiento del lock temporal |
| `processingToken` | string \| null | Functions | token del worker propietario del lock |
| `nextAttemptAt` | Timestamp \| null | Functions | backoff tras un fallo retryable |
| `providerMessageId` | string \| null | Functions | ID devuelto por Resend |
| `createdAt` | Timestamp | Functions | creación del registro |
| `updatedAt` | Timestamp | Functions | última transición |

**Lifecycle:** `onReservaConfirmationCreated` escucha únicamente la creación de `reservas/{resId}`. Crea el documento en `pending`, adquiere un lock transaccional y envía el resumen con la clave externa `confirmation-${encodeURIComponent(reservaId)}`. En éxito cambia a `sent`; ante 429, timeout o 5xx registra `failed`, conserva un error sanitizado y usa backoff hasta tres intentos; ante datos inválidos o fallo permanente termina en `failed`. Las actualizaciones posteriores de la reserva no disparan otro envío y ningún fallo del email modifica o cancela la reserva, que puede seguir `pending` por asignación.

**Ownership and visibility:** solo Firebase Functions mediante Admin SDK crea o actualiza estos documentos. Admin puede leerlos para operación; guest y client no tienen lectura ni escritura. No requiere índice porque se consulta por ID determinístico.

**Rollback:** el cambio es aditivo. Para revertirlo, deshabilitar o retirar `onReservaConfirmationCreated`, conservar `confirmaciones` para auditoría y no borrar documentos ni ejecutar una migración destructiva.

### `empleados/{empId}`

Datos de staff y disponibilidad para la asignación de reservas.

| Campo | Tipo | Generated by | Notas |
|---|---|---|---|
| `name` | string | admin | nombre operativo |
| `role` | 'groomer' \| 'bañador' \| 'cuidador' | admin | rol del empleado |
| `photoUrl` | string \| null | admin | recurso opcional |
| `active` | boolean | admin | baja lógica cuando es `false` |
| `services` | string[] | admin | IDs de `servicios` que puede atender |
| `weeklyShifts` | map | admin | una clave por día: `morning`, `afternoon`, `full` o `null` |

`weeklyShifts` contiene las siete claves `monday`, `tuesday`, `wednesday`, `thursday`, `friday`, `saturday` y `sunday`. `morning` cubre 08:00-14:00, `afternoon` 14:00-20:00 y `full` 08:00-20:00.

**Ownership:** solo administradores pueden leer, crear, actualizar o eliminar documentos de `empleados`. La asignación de `reservas.empleadoId` pertenece a Firebase Functions/Admin SDK; no es un campo controlado por el cliente.

**Reglas:** admin-only total.

### Backfill opcional de `reservas.empleadoId`

El comando es idempotente y funciona en modo dry-run por defecto. Lee `reservas` por lotes y, únicamente con `--apply`, agrega `empleadoId: null` a documentos que no tienen el campo. No asigna empleados ni modifica otros campos. En ambos modos emite un manifiesto JSON con los IDs que serían o fueron afectados; en modo `--apply` solo incluye IDs confirmados dentro de la transacción.

```bash
# Emulador: inspección sin escrituras (modo por defecto)
node tools/backfill-empleado-id.mjs --emulator --manifest /tmp/backfill-empleado-id-dry-run.json

# Emulador: aplicar la normalización
node tools/backfill-empleado-id.mjs --emulator --apply --manifest /tmp/backfill-empleado-id-apply.json

# Cuenta de servicio: siempre indicar explícitamente el archivo
node tools/backfill-empleado-id.mjs --service-account /ruta/serviceAccount.json [--apply] [--manifest /ruta/backfill-manifest.json]
```

El manifiesto contiene `reservationIds`, `mode`, `count` y el campo normalizado. Consérvalo junto con la evidencia de la ejecución para descubrir exactamente los documentos del rollback. Esta tarea no ejecuta el backfill contra producción. Antes de cualquier ejecución productiva futura debe existir un respaldo verificado; el rollback manual consiste en eliminar `empleadoId` únicamente de los IDs del manifiesto de esa ejecución, sin tocar el resto del documento.
