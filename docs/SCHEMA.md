# Firestore Schema

Documento de referencia de las colecciones de Firestore del proyecto `hachi-greciaspa`. Mantenido en sincronía con el código; cualquier cambio de schema debe reflejarse acá y en `firestore.rules`.

Última actualización: 2026-08-04 (Fase 3, modelo de recordatorios).

## Convenciones

- Todos los timestamps usan `serverTimestamp()` desde el SDK cliente.
- Los "snapshots" (`serviceName`, `userName`, `price` en `reservas`) se guardan por inmutabilidad histórica: si el servicio cambia de nombre o precio después de creada la reserva, la reserva conserva los valores del momento de creación.

## Colecciones

### `users/{uid}`

Perfil de usuario. Creado en `register()` (`src/services/auth.ts:29`).

| Campo | Tipo | Generated by | Notas |
|---|---|---|---|
| `email` | string | client | bloqueado a mutación por usuario (rule N1) |
| `displayName` | string \| null | client | |
| `role` | 'client' \| 'admin' | client (always 'client' on signup) | admin reasignado por `set-admin.js` |
| `createdAt` | Timestamp | client | `serverTimestamp()` |

**Reglas:** create si auth.uid == uid && role=='client'; read/update propio o admin; update no puede tocar `role` ni `email` para no-admin (regla N1 de `AUDITORIA.md`).

**Custom claims (Auth):** opcional `admin: true` en el token, complementario al role en Firestore. `set-admin.js` lo setea. Las rules de `isAdmin()` loen ambos.

### `recordatorios/{id}`

Registro de control de recordatorios de cita. El ID es determinístico, con el formato `reminder-${encodeURIComponent(reservaId)}`, para que las ejecuciones horarias reutilicen el mismo documento y no envíen recordatorios duplicados.

| Campo | Tipo | Generated by | Notas |
|---|---|---|---|
| `reservaId` | string | Functions | FK a `reservas/{resId}` |
| `status` | 'pending' \| 'sent' \| 'failed' | Functions | estado del envío |
| `attempts` | number | Functions | intentos acumulados; máximo operativo de tres |
| `scheduledFor` | Timestamp | Functions | fecha y hora objetivo del recordatorio |
| `sentAt` | Timestamp \| null | Functions | instante de envío exitoso |
| `lastAttemptAt` | Timestamp \| null | Functions | último intento de envío |
| `lastError` | string \| null | Functions | categoría de error sanitizada |
| `processingLockUntil` | Timestamp \| null | Functions | vencimiento del lock transaccional temporal |
| `processingToken` | string \| null | Functions | token único que permite aplicar solo la transición del worker dueño del lock |
| `nextAttemptAt` | Timestamp \| null | Functions | no se intenta antes de este instante tras una falla retryable |
| `providerMessageId` | string \| null | Functions | ID devuelto por Resend en el envío exitoso |
| `createdAt` | Timestamp | Functions | creación del registro |
| `updatedAt` | Timestamp | Functions | última transición del registro |

**Lifecycle:** Functions crea el documento en `pending` con `attempts: 0`, `processingToken: null`, `nextAttemptAt: null` y `providerMessageId: null`, adquiere un lock temporal antes de cada envío y aumenta `attempts`. Cada adquisición asigna un token único; las transiciones finales solo se aplican si conservan ese token. El ID determinístico `reminder-${encodeURIComponent(reservaId)}` también se envía como la clave externa de idempotencia del proveedor. En éxito cambia a `sent`, establece `sentAt` y conserva el `providerMessageId`; en una falla retryable cambia a `failed`, conserva una categoría sanitizada en `lastError`, establece `nextAttemptAt` con backoff acotado y libera el lock. En una falla permanente o éxito se limpia `nextAttemptAt`. Las reservas no se modifican por un fallo de email. Los reintentos posteriores solo proceden mientras `attempts < 3` y después de `nextAttemptAt`.

**Ownership and visibility:** solo Firebase Functions mediante Admin SDK crea o actualiza estos documentos; el Admin SDK no depende de los permisos de cliente. Un administrador puede leerlos para operación y debugging. Guest y client no tienen lectura ni escritura; las reglas mantienen `allow write: if false` porque las escrituras de Functions bypassan las reglas de cliente.

**Rollback:** el cambio es aditivo. Para revertirlo, deshabilitar y retirar el scheduled function, conservar `recordatorios` para auditoría y, si corresponde, retirar por separado el índice agregado. No borrar documentos ni ejecutar una migración destructiva.
